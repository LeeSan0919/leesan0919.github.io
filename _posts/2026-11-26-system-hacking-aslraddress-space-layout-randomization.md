# [System Hacking] ASLR(Address Space Layout Randomization)의 원리와 한계

## 1. ASLR이 필요한 이유

시스템 해킹에서 대표적인 공격 기법 중 하나는 BOF(Buffer Overflow)이다.

특히 Stack Buffer Overflow는 버퍼에 허용된 크기보다 많은 데이터를 입력하여 인접한 메모리를 덮어쓰는 취약점이다.

이때 함수의 반환 주소(Return Address)까지 덮어쓸 수 있다면 프로그램의 실행 흐름을 공격자가 원하는 위치로 변경할 수 있다.

그러나 이러한 공격에는 중요한 조건이 있다.

**공격자가 실행 흐름을 이동시킬 정확한 메모리 주소를 알아야 한다는 것이다.**

공격 대상 함수의 주소를 잘못 지정하면 의도한 코드가 실행되지 않고 프로그램이 비정상적으로 종료될 수 있다.

ASLR은 바로 이러한 주소 예측 가능성을 줄이기 위해 도입된 보호기법이다.

## 2. 프로그램의 메모리 구조

프로그램이 실행되면 프로세스의 가상 주소 공간에는 여러 영역이 배치된다.


| 영역 | 역할 |
| -------------- | ------------------------ |
| Stack | 지역 변수, 반환 주소 등 저장 |
| Heap | 동적으로 할당된 데이터 저장 |
| Shared Library | libc 등 공유 라이브러리의 코드와 데이터 |
| Code | main 등 프로그램의 실행 코드 |


주소 배치가 고정되어 있다면 공격자는 한 번 알아낸 함수나 메모리 영역의 주소를 다른 실행에서도 활용할 수 있다.

예를 들어 libc의 `system()` 함수가 항상 동일한 주소에 존재한다면, 공격자는 해당 주소를 이용해 실행 흐름을 변경하려고 시도할 수 있다.

이러한 문제를 완화하는 기법이 ASLR이다.

## 3. ASLR의 동작 원리

ASLR은 Address Space Layout Randomization의 약자로, 주소 공간 배치 무작위화를 의미한다.

프로그램을 실행할 때마다 스택, 힙, 공유 라이브러리 등의 메모리 배치 주소를 무작위화한다.

따라서 동일한 프로그램을 여러 번 실행하더라도 각 영역의 주소가 달라질 수 있다.

리눅스에서는 다음 명령어로 ASLR 설정을 확인할 수 있다.

```
cat /proc/sys/kernel/randomize_va_space
```

설정값의 의미는 다음과 같다.

- `0`: ASLR 비활성화
- `1`: 스택, 공유 라이브러리 등 일부 영역 무작위화
- `2`: 힙을 포함한 추가 영역까지 무작위화

일반적인 리눅스 환경에서는 `2`가 사용된다.

### Stack Canary와의 차이

Stack Canary와 ASLR은 모두 메모리 손상 공격에 대한 보호기법이지만 방어 방식이 다르다.

Stack Canary는 스택의 특정 위치에 검증값을 배치하여 함수 반환 전에 메모리 손상 여부를 확인한다.

반면 ASLR은 메모리 주소를 예측하기 어렵게 만들어 공격자가 원하는 주소로 실행 흐름을 변경하는 것을 방해한다.

즉, Canary는 메모리 손상을 탐지하고 ASLR은 주소 예측을 어렵게 하는 방식이다.

## 4. ASLR과 PIE의 관계

ASLR이 활성화되어 있더라도 실행 파일의 코드 영역이 항상 무작위화되는 것은 아니다.

이때 중요한 개념이 PIE(Position Independent Executable)이다.

PIE는 실행 파일이 고정된 가상 주소에 의존하지 않고 배치될 수 있도록 하는 방식이다.

발표에서는 동일한 프로그램을 PIE 없이 컴파일한 경우와 PIE를 적용한 경우로 나누어 주소 변화를 비교했다.

### PIE 미적용

```
gcc -no-pie
```


| 영역 | 1회차 | 2회차 |
| ----- | -------------- | -------------- |
| Stack | 0x7ffecedae6bc | 0x7fffc2fc0aac |
| Heap | 0x787f2a0 | 0x3f53f2a0 |
| libc | 0x7f34f9060100 | 0x7f6743660100 |
| Code | 0x401166 | 0x401166 |


스택, 힙, libc의 주소는 바뀌었지만 코드 영역의 주소는 동일했다.

### PIE 적용

```
gcc -fPIE -pie
```


| 영역 | 1회차 | 2회차 |
| ----- | -------------- | -------------- |
| Stack | 0x7ffd1e600e5c | 0x7ffde3dc9e7c |
| Heap | 0x557f70c932a0 | 0x55657e5a52a0 |
| libc | 0x7fa206860100 | 0x7fd742a60100 |
| Code | 0x557f588dd179 | 0x556551bd5179 |


이번에는 코드 영역까지 주소가 달라지는 것을 확인할 수 있다.

따라서 실행 파일의 코드 영역까지 주소 무작위화 효과를 적용하려면 일반적으로 ASLR과 PIE가 함께 사용되어야 한다.

## 5. ASLR의 한계

ASLR이 활성화되어 있다고 해서 모든 메모리 공격을 완전히 막을 수 있는 것은 아니다.

### 5.1 메모리 영역 내부의 오프셋은 유지된다

ASLR은 메모리 영역의 배치 주소를 변경하지만 동일한 라이브러리 내부에서 함수들의 상대적 위치는 일반적으로 일정하다.

발표에서 측정한 libc의 주소를 살펴보면 다음과 같다.


| 구분 | 1회차 | 2회차 |
| ---------- | -------------- | -------------- |
| printf 주소 | 0x7f34f9060100 | 0x7f6743660100 |
| libc 시작 주소 | 0x7f34f9000000 | 0x7f6743600000 |
| printf 오프셋 | 0x60100 | 0x60100 |


실행할 때마다 libc의 시작 주소는 변경되지만 `printf` 함수의 오프셋은 동일하다.

따라서 공격자가 실행 중인 프로세스에서 `printf`의 실제 주소를 알아낸다면 다음과 같이 libc 시작 주소를 계산할 수 있다.

```
libc 시작 주소
= printf 주소 - printf 오프셋
```

이후 다른 함수의 오프셋을 알고 있다면 해당 함수의 실제 주소도 계산할 수 있다.

```
system 주소
= libc 시작 주소 + system 오프셋
```

발표에서 사용한 환경에서는 `system`의 오프셋이 `0x58750`이었다.

이처럼 메모리 주소가 외부로 노출되는 현상을 Address Leak이라고 한다.

주소 유출 취약점은 ASLR의 보호 효과를 약화시키는 중요한 원인이다.

### 5.2 주소의 하위 비트가 유지될 수 있다

또 다른 특징은 페이지 단위 메모리 배치이다.

일반적인 시스템에서 메모리 페이지 크기는 4KB, 즉 `0x1000`바이트이다.

페이지 경계에 정렬된 영역의 시작 주소는 하위 12비트가 0이 된다.

따라서 영역 내부에서 동일한 오프셋에 존재하는 주소는 실행마다 상위 주소가 달라져도 마지막 세 자리의 16진수 값이 동일하게 유지될 수 있다.

발표에서 확인한 libc, 힙, 코드 영역의 주소에서도 이러한 특징을 관찰할 수 있었다.

다만 스택 주소는 페이지 내부의 배치와 정렬 등의 영향으로 하위 비트까지 달라질 수 있다.

이러한 특징은 일부 환경에서 Partial Overwrite와 같은 공격을 시도할 때 활용될 수 있다.

## 6. 결론

ASLR은 프로그램의 메모리 주소를 무작위화하여 공격자가 특정 주소를 예측하기 어렵게 만드는 중요한 보호기법이다.

하지만 ASLR은 메모리 손상 취약점 자체를 제거하지 않는다.

또한 주소 유출이 발생하면 라이브러리 내부의 일정한 오프셋을 이용해 다른 함수의 주소를 계산할 수 있다.

따라서 실제 시스템에서는 ASLR만 사용하는 것이 아니라 PIE, Stack Canary 등 여러 보호기법을 함께 적용해야 한다.

이번 발표를 준비하면서 특히 인상적이었던 부분은 **주소가 무작위로 바뀌더라도 메모리 영역 내부의 상대적 위치는 유지된다는 점**이었다.

결국 시스템 보안에서는 단순히 주소를 숨기는 것뿐 아니라 공격자가 주소 정보를 얻을 수 있는 경로를 차단하는 것도 중요하다는 사실을 확인할 수 있었다.
