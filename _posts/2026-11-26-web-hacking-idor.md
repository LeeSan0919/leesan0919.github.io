# [Web Hacking] IDOR 취약점의 원리와 접근 권한 검증

## 1. IDOR란?

IDOR(Insecure Direct Object Reference)는 안전하지 않은 직접 객체 참조를 의미한다.

웹 애플리케이션이 사용자의 요청에 포함된 객체 식별자(ID)를 이용해 데이터를 조회하거나 수정하면서, 해당 객체에 대한 접근 권한을 제대로 확인하지 않을 때 발생하는 취약점이다.

예를 들어 사용자가 자신의 정보를 확인하기 위해 다음과 같은 주소에 접근한다고 가정하자.

```
GET /users/1001
```

그런데 URL의 사용자 번호를 변경했을 때 다른 사용자의 정보가 반환된다면 문제가 발생한다.

```
GET /users/1002
```

핵심은 **서버가 해당 사용자의 로그인 여부만 확인하고, 요청한 데이터에 접근할 권한이 있는지를 확인하지 않았다는 것**이다.

## 2. IDOR의 발생 과정

IDOR는 일반적으로 다음과 같은 과정에서 발생한다.

1. 사용자가 객체 ID를 포함한 요청을 전송한다.
2. 서버는 전달받은 ID에 해당하는 객체를 조회한다.
3. 서버가 사용자별 접근 권한을 검증하지 않는다.
4. 요청한 객체의 데이터가 그대로 반환되거나 수정된다.

여기서 중요한 것은 인증(Authentication)과 인가(Authorization)의 차이다.

인증은 사용자가 누구인지 확인하는 과정이다.

반면 인가는 해당 사용자가 특정 데이터나 기능에 접근할 권한이 있는지 판단하는 과정이다.

따라서 로그인을 정상적으로 완료한 사용자도 다른 사람의 데이터에 접근할 권한까지 갖는 것은 아니다.

## 3. IDOR가 발생하는 위치

객체 식별자는 다양한 형태로 전달될 수 있다.

### 3.1 URL 경로

```
GET /users/1111
```

경로에 포함된 사용자 ID를 변경하는 방식이다.

### 3.2 Query String

```
GET /users?memberId=1111
```

URL의 쿼리 파라미터를 변경하는 방식이다.

### 3.3 HTTP 요청 본문

```
{
  "memberId": 1111
}
```

요청 본문에 포함된 식별자도 검증 대상이다.

따라서 주소창에 ID가 보이지 않는다고 해서 IDOR 취약점이 발생하지 않는 것은 아니다.

서버가 사용자가 전달한 객체 ID를 신뢰하고 접근 권한을 검사하지 않는다면 다양한 요청에서 동일한 문제가 발생할 수 있다.

## 4. API 환경에서의 IDOR

현대 웹 서비스는 프런트엔드와 백엔드가 API를 통해 통신하는 경우가 많다.

예를 들어 사용자 A가 다음 요청을 보냈다고 가정하자.

```
GET /api/orders/102
```

그런데 102번 주문의 실제 소유자가 사용자 B라면 서버는 해당 요청을 거부해야 한다.

만약 서버가 주문번호만을 기준으로 주문 정보를 반환한다면 사용자 A가 사용자 B의 주문 정보를 확인할 수 있게 된다.

API 보안에서는 이러한 객체 수준 인가 실패를 BOLA(Broken Object Level Authorization)라고 부른다.

IDOR는 BOLA 취약점을 설명할 때 대표적으로 등장하는 사례이다.

## 5. 수평적 권한 상승과 수직적 권한 상승

접근 권한 문제는 크게 수평적 권한 상승과 수직적 권한 상승으로 구분할 수 있다.

### 5.1 수평적 권한 상승

수평적 권한 상승은 동일한 권한 수준을 가진 다른 사용자의 자료에 접근하는 경우다.

예를 들어 일반 사용자 A가 다른 일반 사용자 B의 정보를 조회한다고 가정하자.

```
GET /mypage/info?memberId=1111 HTTP/2
Host: insecure-web.com
```

서버가 사용자 A에게 B의 정보를 반환한다면 수평적 권한 상승이 발생한 것이다.

정보 조회뿐 아니라 수정 요청에서도 같은 문제가 발생할 수 있다.

```
PUT /mypage/info/1111 HTTP/2
Host: insecure-web.com

phone=010-1111-1111
```

객체별 권한 확인이 없다면 타인의 전화번호처럼 중요한 정보를 임의로 변경할 수도 있다.

### 5.2 수직적 권한 상승

수직적 권한 상승은 일반 사용자가 관리자 등 상위 권한에 속하는 자료나 기능에 접근하는 경우다.

```
GET /reports/101
```

101번 보고서는 일반 사용자에게 허용된 자료라고 가정하자.

반면 다음 보고서는 관리자 전용이다.

```
GET /reports/900
```

일반 사용자가 900번 보고서를 요청했을 때 서버가 관리자 권한을 확인하지 않고 내용을 반환한다면 상위 권한 자료에 대한 접근 통제가 실패한 것이다.

두 경우 모두 공통적으로 서버의 인가 검증이 부족하다는 문제가 있다.

## 6. IDOR 취약점 방어 방법

가장 중요한 해결 방법은 서버에서 객체별 접근 권한을 검증하는 것이다.

예를 들어 사용자 A가 102번 주문을 요청했다면 서버는 다음과 같은 과정을 거쳐야 한다.

```
사용자 A → /orders/102 요청
               ↓
서버가 102번 주문 조회
               ↓
현재 로그인한 사용자가
102번 주문에 접근할 권한이 있는가?
               ↓
       ┌───────┴───────┐
       │               │
      YES              NO
       │               │
    자료 반환        접근 거부
```

이때 사용자의 신원은 요청 본문이나 URL에 포함된 사용자 ID를 그대로 신뢰하는 것이 아니라, 서버에서 검증한 로그인 세션이나 인증 정보에 기반해야 한다.

또한 주문번호를 복잡하게 만드는 방식도 생각해볼 수 있다.

```
기존 주문번호: 102
변경 주문번호: 364372462371129330969
```

이렇게 하면 다른 객체의 ID를 추측하기 어려워질 수 있다.

하지만 식별자를 복잡하게 만든다고 해서 권한 검증이 이루어지는 것은 아니다.

**ID를 숨기는 것은 인가 검증을 대신할 수 없다.**

## 7. 결론

IDOR는 매우 복잡한 공격 기법이 아니라 서버의 접근 권한 확인이 누락되면서 발생하는 취약점이다.

특히 로그인 기능이 정상적으로 구현되어 있더라도 객체별 인가 검증이 빠져 있다면 다른 사용자의 데이터가 노출될 수 있다.

이번 발표에서 가장 중요하게 다룬 부분도 바로 인증과 인가의 차이였다.

사용자가 누구인지 확인하는 것과 해당 사용자가 어떤 데이터에 접근할 수 있는지를 판단하는 것은 별개의 문제이다.

따라서 안전한 웹 애플리케이션을 개발하기 위해서는 모든 데이터 조회 및 변경 과정에서 객체별 접근 권한을 확인해야 한다.
